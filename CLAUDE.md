# Allure+

App perso de suivi sportif (Node.js/Express + JS vanilla), intégrée à Garmin Connect et Campus Coach. Utilisateur : Stéphane Martin (compte in-app `shiznogoud@gmail.com`).

## Architecture

- `server.js` — toutes les routes API, sessions en mémoire (cookie `sid`), auto-login via `.env`.
- `garmin_client.js` — wrapper autour de la lib `garmin-connect` (activités, VO2max, records calculés, etc.).
- `campus_client.js` — client Campus Coach (plans d'entraînement).
- `frontend/index.html` — page unique, toutes les "pages" sont des `<div class="page" id="page-X">` togglées en JS.
- `frontend/js/app.js` — dashboard, profil, activités, records (page shell), helpers globaux (`el`, `formatDate`, `formatPace`, `showToast`, `showConfirmModal`...).
- `frontend/js/campus.js` — Entraînements, Objectifs, tout ce qui touche aux plans Campus/importés.
- `frontend/js/plans.js` — catalogue de plans (wizard de recherche), chargement d'un plan.
- `frontend/js/stats.js` — page Statistiques (lignes par année, comparaison).
- `frontend/js/records.js` — page "Records et courses" (records éditables + tableau de courses).
- `frontend/js/health.js` — page "Santé/Performance" (2 catégories, cartes valeur+historique+commentaire personnalisé par indicateur).
- `frontend/css/style.css` — styles globaux ; `frontend/css/plans.css` — styles spécifiques à la page Plans.
- `zones.js` — source de vérité serveur des zones d'allure (`ALLURE_PLUS_ZONES`), utilisée par `server.js` et `xlsx_export.js`.
- Scripts chargés dans cet ordre dans `index.html` : `app.js`, `campus.js`, `stats.js`, `records.js`, `health.js`, `plans.js` — un `const`/`function` défini dans un script est utilisable par les scripts suivants (scope global partagé).

### Données persistantes protégées (jamais commitées, jamais écrasées par l'installeur)
- `data/records_overrides.json` — corrections manuelles des 5 records personnels.
- `data/races.json` — tableau "Mes courses" (saisie libre).
- `data/user_data.json` — miroir serveur des clés `localStorage` "durables" (voir point d'architecture ci-dessous).
- `data/activities_cache.json` — cache serveur des activités Garmin par année passée et close (voir point d'architecture ci-dessous). Simple cache (jamais l'année en cours) : sa perte est sans gravité, contrairement aux fichiers ci-dessus.
- `uploads/` — avatar utilisateur, diplômes de course (PDF/image).
- `Images/` — photos du diaporama de fond (jamais écrasé au reinstall si non-vide, voir `ShouldSeedImages` dans le `.iss`).
- Tous listés dans `.gitignore` ET exclus explicitement dans `installer/allure-plus.iss` (`Excludes` + `Check: ShouldSeedImages` pour `Images/`).

### Points d'architecture notables
- **Records personnels** (`/api/records`) : calculés par défaut depuis Garmin (`getPersonalRecords`, limité aux 200 dernières activités), mais **n'affichent rien tant que l'utilisateur n'a pas saisi une première valeur manuelle** (pas de pré-remplissage automatique). Une fois une correction manuelle en place, si une activité Garmin plus récente la bat, un bandeau propose de l'adopter (jamais de remplacement silencieux) — refus mémorisé dans `localStorage` pour ne pas reproposer la même activité en boucle.
- **Paliers D+ trail** (`TRAIL_DPLUS_TIERS` dans `server.js`) : référence unique (Peu vallonné/Vallonné/Montagneux/Très montagneux) par catégorie de distance (court/moyen/long/ultra), affichée sur la page Admin. Utilisée pour classer les plans du catalogue (`plans/trail/...`).
- **Barre "Avancement du plan"** (Objectifs) : position continue au prorata des jours écoulés (pas par semaine entière), graduations + numéro de semaine par section.
- **Version app** : `package.json` → champ `version`, affiché dans la sidebar (`v{version}`), exposé via `/api/status`. L'installeur (`#define MyAppVersion`) doit être synchronisé manuellement. Convention : bump à chaque fonctionnalité/correctif notable (minor pour feature, patch pour fix).
- **Page Santé/Performance** (`frontend/js/health.js`) : certaines métriques Garmin (Âge physique, Prédicteur de course, Score de montée, Score d'endurance, Tolérance de course) sont passées côté Garmin sur un proxy web `connect.garmin.com/gc-api/...` qui exige une session de navigateur (cookies + jeton anti-CSRF) — inaccessible depuis notre client OAuth (`connectapi.garmin.com`, utilisé par `garmin_client.js`), qui renvoie 403 sur ce chemin. Vérifié via DevTools sur le compte réel : aucune requête directe vers `connectapi.garmin.com` n'existe pour ces 5 métriques. Elles ne sont donc pas exposées dans Allure+ (chantier d'authentification navigateur complet jugé disproportionné pour 5 indicateurs secondaires) — ne pas retenter sans nouvelle piste concrète.
- **Statut d'entraînement** (Santé/Performance) : Garmin n'expose pas d'historique par API pour cet indicateur — Allure+ construit sa propre courbe en capturant un instantané par jour (`captureHealthSnapshot`, `data/health_snapshots.json`) à chaque consultation. Affiché en bande "façon Garmin Connect" (une case par jour, vide si non visité ce jour-là) plutôt qu'en tableau texte.
- **Zones d'allure (`ALLURE_PLUS_ZONES`)** : source de vérité **unique** dans `frontend/js/campus.js`, mirroir strict dans `zones.js` (serveur) — les deux fichiers doivent rester synchronisés manuellement (commentaires croisés dans chaque fichier). Toutes les autres surfaces qui affichent ces zones (tableau Allures du Profil, modale "Voir mes allures" dans Objectifs, carte "Allure EF" des indicateurs, `xlsx_export.js`) **lisent directement `ALLURE_PLUS_ZONES`** (via `calcAllureRef`/`calcAllureRefTrail` côté front, `getZoneRange` côté serveur) — ne jamais recréer une copie locale des % VMA, c'est exactement ce qui a causé un bug de zones incohérentes entre deux tableaux (nov. 2026). Le champ `fcZone` sur chaque entrée est une correspondance FC qualitative fournie par l'utilisateur (pas calculée), affichée en plage ("Z3 haute à Z4 basse") — jamais en valeur unique, une zone FC (%FC réserve) et une zone d'allure (%VMA) ne se recouvrant jamais exactement.
- **PPS (Pass Prévention Santé)** : à l'import d'un PDF, extraction du numéro/nom/date **en priorité via le QR code** du document (`pdfjs-dist` + `jsQR` dans `server.js`, fonction `extractPpsFromQr`) — le QR pointe vers une URL `pps.athle.fr` dont le paramètre `data` est un JSON structuré (base64url + zlib deflate), bien plus fiable que l'ancienne heuristique de position dans le texte brut du PDF (conservée en repli si le QR est absent/illisible, autre gabarit de PPS).
- **Persistance des données "durables" du profil** (`DURABLE_LS_KEYS`/`DURABLE_LS_PREFIXES` dans `frontend/js/app.js`) : le profil (sexe/date de naissance/taille/poids), les objectifs personnels, le plan importé et le suivi des séances pointées comme faites vivaient **uniquement en `localStorage`**, sans aucune autre source (contrairement aux activités, toujours re-téléchargeables depuis Garmin) — un nettoyage de l'historique de navigation (incident réel, 09/08) a fait perdre tout ça d'un coup, y compris des effets de bord non évidents (ex : couleur du VO2max faussée car dépendante du sexe lu dans le profil vide → mauvais barème). `localStorage.setItem` est patché pour ces clés précises : chaque écriture est mirorée vers `/api/user-data` (→ `data/user_data.json`, protégé comme le reste de `data/`) **en plus** du `localStorage` habituel, sans toucher aux dizaines d'appels `localStorage.getItem/setItem` existants ailleurs (campus.js, plans.js, records.js...) qui continuent de lire/écrire `localStorage` normalement — la synchro est transparente. Au démarrage (`syncUserDataFromServer()`, tout début du handler `DOMContentLoaded`), synchro **bidirectionnelle** : comble les clés manquantes en local depuis le serveur (récupération après un nettoyage), ET pousse immédiatement vers le serveur les clés déjà en local mais jamais encore synchronisées (sans attendre une future écriture qui pourrait ne jamais arriver avant un nouveau nettoyage) — ne jamais écraser une valeur locale déjà présente par une copie serveur potentiellement périmée. **Multi-appareils (20/08)** : cette dernière règle ("jamais écraser si déjà présente") empêchait à tort la réception des mises à jour faites sur un AUTRE appareil dès qu'une machine avait déjà sa propre valeur locale pour une clé donnée (souvent vide) — bug réel constaté (compte de l'épouse, PC du bureau) : séances pointées "faites" et ressenti (`suivi_local_done`/`suivi_session_mood`) saisis sur son PC perso jamais répercutés sur le PC du bureau, alors que la liaison/analyse de séance (`session_analyses`, fusion fine par élément côté `sync.js`) arrivait bien. `GET /api/user-data` renvoie désormais `{ data, meta }` (`meta[cle]` = `updatedAt` tiré du sidecar `data/user_data.sync.json`, déjà tenu à jour par `sync.js`/`runFullReconciliation` à chaque pull cross-appareils) ; le client retient dans `localStorage['_durable_sync_applied_meta']` (purement locale, jamais synchronisée, purgée au `logout()` comme le reste) le dernier `updatedAt` serveur déjà adopté par clé, et n'adopte une valeur serveur que si elle est absente en local OU strictement plus récente que ce marqueur — une édition locale plus fraîche reste protégée comme avant.
- **Cache serveur des activités par année** (`/api/activities/year/:year` dans `server.js`, `data/activities_cache.json`) : le cache des années passées vivait uniquement en `localStorage` cote client (`stats.js`, `allure_year_cache_v1_*`) — perdu lui aussi au nettoyage du navigateur du 09/08, obligeant à recliquer "Cliquez pour charger" annee par annee sur la page Statistiques. Deplace cote serveur, directement dans la route qui appelle Garmin : les annees **passees et closes** (`year < currentYear`, elles ne changeront plus jamais) sont lues/ecrites dans ce fichier ; **l'annee en cours n'est JAMAIS mise en cache** et repart toujours chercher les donnees fraiches chez Garmin (nouvelles activites en continu) — meme frontiere que l'ancien cache client, juste deplacee plus haut pour survivre a n'importe quel navigateur/nettoyage. Cote client, `renderStatsYearsList` (stats.js) charge desormais automatiquement toutes les annees affichees au lieu d'attendre un clic — rapide grace a ce cache serveur, donc plus besoin d'action utilisateur. Contrairement a `user_data.json`, la perte de ce fichier n'est jamais grave (juste un aller-retour Garmin en plus au prochain chargement) — **ne pas** le vider via `/api/refresh` (bouton "Actualiser les donnees"), qui ne concerne que le cache Garmin interne (`cache.json`) et le tableau de bord, pas les annees passees.
- **Campus Coach masqué pour les autres profils (09/2026)** : la fonctionnalité Campus Coach reste **entièrement codée et fonctionnelle** (routes serveur, sync du plan, UI) mais n'est **affichée qu'au compte `shiznogoud@gmail.com`** — décision volontaire, pas un chantier en cours : aucun autre utilisateur d'Allure+ n'a de compte Campus Coach actuellement, autant ne pas les perturber avec cette option tant que ça reste vrai. Gate unique côté serveur : `campusVisibleForSession()` (`server.js`), qui combine le flag global `CAMPUS_ENABLED` (`.env`, par machine) avec un contrôle par compte (`CAMPUS_VISIBLE_EMAIL`) — exposé via `campusEnabled` dans `/api/campus/status`. Pour les autres comptes, ce `campusEnabled: false` réutilise tel quel le chemin déjà existant "pas de compte Campus" (`showTrainingEmpty()` dans `campus.js` : masque le formulaire de connexion Campus, garde l'import de plan `.aplus` toujours visible) — donc les autres profils gardent la possibilité d'importer un plan partagé, seule la proposition de connexion Campus Coach disparaît (Profil > Applications connectées, et l'écran de premier lancement `login.html` où la section "Compte Campus Coach" ne s'affiche que si l'e-mail Garmin saisi correspond). Pour rouvrir à tout le monde : supprimer l'appel à `campusVisibleForSession()` dans `/api/campus/status` (repasser `campusEnabled: CAMPUS_ENABLED`) et retirer le gate par e-mail dans `login.html`.
- **Analyse détaillée d'une séance trail — pente réelle & GAP** (`buildSessionAnalysis` dans `frontend/js/session-analysis.js`) : sur une séance trail/côte/D+, l'allure cible affichée (ligne "Allure") est la cible plate **déjà majorée** d'un forfait fixe par zone (`trailCorr` dans `ALLURE_PLUS_ZONES`, campus.js — ex +7% pour EF), donc comparer l'allure brute réelle à cette cible pénalise deux fois le dénivelé sur les sections très pentues (faux positifs "trop lent" constatés avec l'utilisateur). Le vrai verdict conforme/pas conforme utilise le **GAP** (`avgGradeAdjustedSpeed`, déjà présent sur chaque lap via `/api/activity/:id/laps` — aucun appel Garmin supplémentaire nécessaire) comparé à la cible **plate non ajustée** (`calcAllureRef`, pas `calcAllureRefTrail`) — champ `climbAnalysis`/`trail.climb`, variable `effectiveDeviationSecKm` qui remplace `deviationSecKm` pour `paceVerdict`/anomalies/score sur les séances TRAIL uniquement (non-trail inchangé). La ligne "Allure" (brute vs ajustée) reste affichée telle quelle, mutée, uniquement pour donner une idée du temps réel passé — ne jamais la supprimer (demande explicite utilisateur). Pente moyenne/max/% distance en côte et FC côte-vs-plat sont calculées depuis la trace GPS fine de l'activité (`computeGradeSegments`, session-analysis.js — regroupée en tronçons de ~50m, seuil `CLIMB_GRADE_PCT = 3%`), **pas** depuis les laps Garmin (1km ou plus) : un lap entier dilue une côte courte et répétée (ex: 320m/45m D+, ~14%) en une pente nette quasi nulle dès que le reste du lap redescend ou est plat — bug réel constaté (3.9% affiché au lieu de ~14%) avant ce passage à la trace GPS. La trace GPS (route `/api/activity/:id/gps`, champ `elevation` — distance/altitude/FC/GAP par point, ~10-50m entre points selon la longueur de l'activité, cf. `MAX_PTS=600` dans `server.js`) est réutilisée telle quelle pour le profil altimétrique de la course ; seul le GAP moyen affiché reste calculé depuis les laps (`avgGradeAdjustedSpeed`, identique à la colonne "GAP moyenne" de Garmin Connect). Section "Pente & effort en côte" affichée uniquement dans la modale d'analyse détaillée d'une séance (jamais ailleurs).
- **Fiche utilisateur détaillée (Admin)** : Allure+ est distribué en `.exe`, chaque compte tourne sur sa propre machine avec son propre `data/` local (jamais versionné, jamais accessible directement à l'admin) — mais un système de synchro cross-appareils existe déjà (`sync.js`/`sync-relay/`, Cloudflare Worker + KV scopé par e-mail Garmin) pour que le même compte retrouve ses données sur un second PC (profil, plan importé, PPS, avatar...). La fiche dépliante du panel Admin (`toggleAdminUserDetail`/`renderAdminUserDetail` dans `app.js`, route `/api/admin/users/:email/details` dans `server.js`) **lit ces mêmes types déjà synchronisés** (`user_data`, `health_snapshots`) via `syncClient.pullEnvelope()` — aucun nouveau type, aucun redéploiement du Worker nécessaire. Portée volontairement limitée (demande explicite utilisateur) : sexe/âge (`suivi_sport_profile`), plan suivi + libellé (`suivi_imported_plan.goal.planCategory`, injecté par `/api/plans/load/:id` depuis le nom du fichier `.aplus` catalogue) + assiduité (séances dues des semaines déjà commencées vs `suivi_local_done`), et VO2max — **jamais** avatar/PPS/diplômes (hors sujet pour l'admin). Le VO2max est un cas particulier : jamais stocké par Allure+ normalement (toujours redemandé en direct à Garmin), il est désormais capturé côté serveur à chaque chargement du dashboard via `captureHealthSnapshot('vo2max', ...)` — **exactement le même mécanisme déjà utilisé pour "Statut d'entraînement"**, donc déjà synchronisé sans rien ajouter côté Worker. Ce point est **strictement à sens unique** : rien dans l'app ne relit jamais la clé `vo2max` de `health_snapshots` localement (seule la route Admin l'interroge via `pullEnvelope`), donc cette valeur ne peut jamais écraser le VO2max Garmin affiché en direct dans l'UI — condition explicite de l'utilisateur.
- **Suivi du catalogue de plans** (page Plans d'entraînement, section repliable visible uniquement pour `shiznogoud@gmail.com` via `showAdminNav`) : tableau route (5/10/20-Semi/Marathon/50/100 km) et trail (catégories × paliers D+ de `TRAIL_DPLUS_TIERS`, seule source de vérité, jamais dupliquée côté client — le serveur renvoie `trailCategories` calculé depuis cette même table) croisés avec ACTIF/PAUSE/REPRISE et 3 à 6 jours/semaine (2j/semaine volontairement retiré, jugé trop peu pour un plan structuré). Présence = scan réel des fichiers `.aplus` (`getAllPlanFiles`/`parsePlanMeta`, route `/api/admin/plans-catalog`) — jamais une liste figée qui pourrait déraper des vrais fichiers. Chaque créneau est en **tri-state** (`plansAdminDayChips`, `frontend/js/plans.js`), pas une simple case à cocher : vert + case cochée+désactivée = fichier(s) réellement présent(s) sur le disque (l'état ne se coche jamais manuellement, il ne peut que refléter la réalité du disque) ; rouge + case cochée = créneau vide **volontairement exclu** par un clic manuel (persisté `true` dans `data/plan_publish_flags.json`) — sémantique inverse de l'ancienne version : cocher une case vide signifie désormais « je ne proposerai jamais ce plan » (ex : pas de plan Marathon à 2 jours/semaine), pas « à faire » ; gris + décoché = pas encore tranché. Si un fichier apparaît un jour sur un créneau marqué exclu, l'état passe automatiquement au vert (présence prime toujours sur le flag manuel, jamais l'inverse). `durations` (semaines, dédupliquées/triées, dérivées de `meta.duree`) est renvoyé par créneau et affiché en `<sup>` + détail dans le `title` du chip plutôt qu'en colonne dédiée, pour ne pas faire exploser la taille du tableau. `setPlanPublishFlag` (plans.js) ré-affiche tout le tableau après chaque clic (`renderPlansAdminTracker(_plansAdminData)`) car la couleur d'un chip dépend de `flags`, pas seulement de `checked` — un simple changement natif de la case ne suffirait pas à la faire virer au rouge. **N'affecte jamais** le catalogue réellement montré aux utilisateurs dans le wizard Plans (aucun filtre appliqué côté `plans.js`/`/api/plans`), c'est une checklist de préparation personnelle, pas un contrôle de publication.
- **Cohérence des `page-header`** : tous les headers de page partagent la même position (coin haut-gauche, largeur) car `.page` (style.css) fixe un padding unique — **ne jamais ajouter de padding spécifique à une page** (`#page-X{padding:...}`) sans reprendre exactement `32px`/`36px` en haut/côtés, sous peine de décaler ce header par rapport aux autres. `scrollbar-gutter:stable` sur `html` évite aussi un décalage de ~4px selon qu'une page a ou non une barre de défilement.
- **Globe 3D des activités** (bouton "Globe" dans le groupe `#act-view-toggle`, page Activités — `frontend/js/globe.js`) : moteur **CesiumJS** (CDN `cdn.jsdelivr.net/npm/cesium`, `window.CESIUM_BASE_URL` fixé avant le `<script>` Cesium pour que ses workers/assets se résolvent depuis le même CDN) — remplace un premier essai avec `globe.gl` (texture terrestre unique), abandonné car le zoom ne pouvait que grossir les mêmes pixels sans jamais révéler de détail (contrainte utilisateur explicite : "pas de flou, net à tout niveau de zoom"). Imagerie = tuiles raster **CARTO `dark_all`** (`{s}.basemaps.cartocdn.com/dark_all/{z}/{x}/{y}{r}.png`, même famille OSM/CARTO déjà utilisée pour les cartes de trace GPS ailleurs dans l'app, mais style sombre plutôt que "voyager" clair) via `Cesium.UrlTemplateImageryProvider` — **aucun compte/jeton Cesium Ion** (`Ion.defaultAccessToken` laissé vide, `terrainProvider: EllipsoidTerrainProvider` = pas de relief, aucune fonctionnalité payante). Les marqueurs (cercles + halo, couleur/taille sur une **échelle log** du nombre d'activités groupées — sinon un lieu "domicile" à 50-100+ sorties écrase visuellement les zones isolées) sont de **vrais éléments DOM** repositionnés à chaque frame via `Cesium.SceneTransforms` (lat/lng → coordonnées écran) plutôt que des primitives Cesium natives, pour garder le contrôle CSS total sur le halo (`radial-gradient` + `box-shadow`) — les points proches sont d'abord regroupés par grille (~8km) avant d'être transformés en éléments, sinon des dizaines de sorties au même endroit produiraient autant de cercles empilés. Cliquer un cercle vole la caméra dessus (`camera.flyTo`).
  Les points viennent de `startLat`/`startLon`, exposés par `/api/dashboard` et `/api/activities/year/:year` depuis `startLatitude`/`startLongitude` — déjà présents tels quels dans la réponse Garmin de la liste d'activités (vérifié en direct), donc **aucun appel Garmin supplémentaire**. **Deux caches à surveiller** si ce champ change encore un jour : le cache serveur des années passées (`data/activities_cache.json`) ET un **cache navigateur `localStorage`** plus ancien (`allure_year_cache_v1_*`, `stats.js`, `ensureYearLoaded`/`loadYearFromCache`) interrogé *avant* le serveur par le filtre "Toutes les années" de la page Activités — bug réel constaté (total correct mais nombre de points géolocalisés bloqué à celui de l'année en cours) causé par ce second cache, jamais invalidé par la migration côté serveur puisqu'il la court-circuite entièrement. Les deux caches détectent maintenant la même chose (`cached[0].startLat === undefined` → cache ignoré, refetch forcé qui le repeuple). Les points affichés suivent exactement les mêmes filtres que le tableau Activités (sport/année/mois/recherche, `_lastFilteredActivities` alimenté par `renderAllActivities`, `app.js`) — pas de logique de filtre dupliquée. Le rafraîchissement du globe pendant que la modale est ouverte est **debounce (300ms)** : "Toutes les années" déclenche ~15 appels successifs (un par année), et sans ce debounce le compteur clignotait à travers des valeurs intermédiaires avant de se stabiliser.
- **Connexion Garmin avec MFA (code SMS)** (`garmin_mfa_patch.js`, chargé par `server.js` juste après `require('garmin-connect')`) : la lib `garmin-connect@1.6.2` utilisée ici n'a **aucun support MFA fonctionnel** — `HttpClient.prototype.handleMFA` est un no-op vide avec un `// TODO: Handle MFA` laissé par l'auteur (vérifié dans `node_modules/garmin-connect/dist/common/HttpClient.js`), donc les comptes avec le MFA activé côté Garmin ne pouvaient jamais se connecter (erreur générique "Ticket not found or MFA"). Il existe une pull request ouverte mais **non fusionnée/non publiée sur npm** sur le dépôt de la lib qui implémente ce flux (`GarminMfaRequiredError` + `resumeWithMfa(code)`) — plutôt que d'en dépendre directement (ce qui obligerait tous les postes utilisateurs à compiler du TypeScript à l'installation, l'installeur excluant `node_modules` et lançant `npm install` en local, cf `installer/allure-plus.iss`), la logique MFA de cette PR est **reproduite en monkeypatch** du prototype `HttpClient` partagé (import profond `garmin-connect/dist/common/HttpClient` — possible car le `package.json` de la lib n'a pas de champ `exports` qui le bloquerait). Le reste de l'enchaînement OAuth (`getOauth1Token`, `exchange`) est réutilisé tel quel, ce sont des méthodes déjà existantes et déjà utilisées avec succès par la connexion normale.
  Côté serveur (`server.js`) : `createGarminSession` attache l'instance `gc` en cours à l'erreur `GarminMfaRequiredError` avant de la relancer (jamais recréer une instance fraîche pour reprendre — l'état de connexion en cours, cookies + `_mfaLoginState`, vit sur cette instance précise) ; `/api/setup` et `/api/login` la mettent en attente dans `pendingMfaLogins` (Map en mémoire, TTL 5 min) et répondent `{mfaRequired:true, mfaToken}` au lieu de l'erreur générique habituelle ; `/api/login/mfa` (nouvelle route) reprend avec `gc.resumeWithMfa(code)` puis rejoue exactement la suite normale (`finalizeGarminSession`, et pour `/api/setup` spécifiquement `finishSetup` — extrait de l'ancien corps de la route pour être rejouable à l'identique). Un code erroné **ne supprime pas** l'entrée en attente (Garmin laisse plusieurs essais sur le même défi MFA) — seul un succès ou l'expiration du TTL la retire. Côté `frontend/login.html`, une troisième carte (`#mfa-card`, à côté de `reconnect-card`/`setup-card`) s'affiche quand `doAutoLogin()`/`doSetup()` reçoit `mfaRequired`. Une fois le token OAuth obtenu (avec ou sans MFA), il est sauvegardé sur disque (`gc.exportTokenToFile`) et réutilisé aux démarrages suivants (`restoreGarminSession`) — **le code SMS n'est donc redemandé qu'à la première connexion**, pas à chaque lancement de l'app. **Premier retour réel (21/08, compte d'un collègue)** : toujours le message générique, malgré ce correctif. Diagnostic capturé via un dump du HTML reçu (`data/garmin_login_debug.html`, écrit par `handleMFA` quand ni la détection MFA ni le ticket normal ne matchent) — le HTML était une page de connexion **vierge**, structurellement identique à un tout premier chargement (`isUsernameDefined`/`result` vides côté serveur, aucun champ pré-rempli, aucun message d'erreur), alors que le compte a bien le MFA activé (confirmé : code SMS demandé en se connectant sur connect.garmin.com dans un vrai navigateur). Cause racine trouvée : `HttpClient.js` de la lib **ne gère aucun cookie** entre ses requêtes (zéro occurrence de "cookie" dans le fichier — son client HTTP est un `axios.create()` nu). Le flux de connexion enchaîne pourtant plusieurs requêtes (GET page de connexion → GET jeton CSRF → POST identifiant/mot de passe) que Garmin relie normalement via un cookie de session. Sur un compte **sans** MFA ça ne se voyait jamais : Garmin délivre le ticket dès la 3ᵉ requête, le jeton CSRF seul suffit. Mais le flux MFA a besoin de cette continuité de session entre "la requête qui soumet le mot de passe" et, plus tard, "la requête qui soumettra le code SMS" — sans cookie transmis, Garmin ne reconnaît pas la 2ᵉ requête comme faisant partie de la même connexion et retombe sur la page vierge. Corrigé par un cookie jar minimal (mémoire, nom=valeur seulement, pas de scope domaine/path/expiration — tout le flux reste sur le même hôte SSO et dure quelques secondes) installé via une sous-classe `HttpClientWithCookies` qui enveloppe le constructeur (impossible d'intercepter `this.client = axios.create()` en ne patchant qu'un prototype) et réaffectée sur l'objet `module.exports` partagé de `HttpClient` (`GarminConnect.js` y accède en lecture directe à chaque connexion, `HttpClient_1.HttpClient(url)` — pas une valeur figée à son propre `require()`, donc la réaffectation est prise en compte même faite après coup). Vérifié par un test bout-en-bout contre un serveur HTTP local (cookie posé sur une 1ère requête bien renvoyé sur la 2ᵉ). **2ᵉ passe (toujours 21/08)** : l'écran MFA s'affichait désormais (preuve que le cookie jar fonctionne), mais la soumission du code plantait avec "Cannot read properties of undefined (reading 'headers')" — cause réelle : Garmin répond HTTP 401 à cette requête, et l'intercepteur response *partagé* de la lib (constructeur `HttpClient`, pensé pour rafraîchir un token OAuth2 expiré sur des appels API *après* connexion) avale n'importe quel 401 en le résolvant avec `undefined` quand `this.oauth2Token` n'est pas encore défini (toujours le cas pendant le flux SSO lui-même) — notre propre intercepteur de cookies, enregistré après, plantait alors sur ce `undefined`. Corrigé par une garde défensive sur `response`, et surtout par `_retry: true` posé dès le départ sur cette requête précise (le même flag que la lib pose normalement après une 1ère tentative pour ne jamais boucler) afin de court-circuiter entièrement cette logique de retry OAuth2 qui n'a rien à voir avec le flux de connexion. **3ᵉ passe** : le vrai 401 de Garmin, enfin visible, montrait le formulaire identifiant/mot de passe avec "Invalid sign in" — preuve que la requête atterrissait sur le gestionnaire de connexion standard (`/sso/signin`), jamais sur celui de vérification MFA. Cause : le formulaire MFA réel n'a pas d'attribut `action` (il se soumet à "l'URL actuelle"), et `enterMfaCode.js` (script Garmin récupéré directement depuis `sso.garmin.com` pour inspection, fichier public sans authentification) navigue entre plusieurs URLs sous `/sso/verifyMFA/...` — la page MFA est donc servie via une redirection HTTP après le POST identifiant/mot de passe, qu'axios suit tout seul sans que le code n'ait jamais capturé l'URL finale réelle (il reconstruisait à tort `/sso/signin`). Corrigé en captant `response.request.res.responseUrl` (exposé par l'adaptateur Node d'axios) dans l'intercepteur du cookie jar à chaque réponse, et en postant le code vers cette dernière URL capturée plutôt qu'une URL reconstruite. **Confirmé fonctionnel en conditions réelles le 21/08** (le même jour, sur le compte du collègue) : connexion complète réussie avec code MFA.

- **Alertes Garmin "Répétition k/N" + export des points d'intérêt** (Itinéraires et Éditeur Parcours, 25/08) : retour terrain explicite — sur une côte à répéter, les chevrons indiquent le sens mais rien n'indiquait combien de fois il restait à la remonter. `buildGpxXml` (`route_generator.js`) accepte désormais un 3ᵉ paramètre `waypoints` (`{lat,lon,name,sym}[]`), émis en `<wpt>` **avant** `<trk>` (ordre imposé par le schéma GPX 1.1) — ce sont des "Course Points" Garmin : la montre affiche une alerte pop-up avec `name` en approchant du point pendant la navigation d'un parcours importé. `POST /api/routes/gpx` (`server.js`) transmet `waypoints` tel quel, sans validation lourde (mêmes garanties que `points`). **Convention de comptage à ne jamais mélanger entre les deux mécanismes de répétition de l'app** (vérifié empiriquement, cf tests Node ad hoc) : côté générateur (`repeatedSegments[].reps`), `reps` compte les passages **additionnels** au sommet, en plus de la montée naturelle déjà dans la boucle de base → nombre total de montées = `reps + 1` (`routes.js`, `buildRepeatWaypoints`) ; côté Éditeur (`buildMultiRepeatedPoints`, champ "Nombre de montées souhaité"), le nombre saisi est déjà le **total** de montées, pas de +1. Côté Éditeur, aucune trace d'une répétition n'était gardée après application (juste le tracé brut résultant) — nouveau champ `_routeEditorData.repeats` (array `{lat, lon, totalPasses}`, coordonnée B de la section = le point où chaque passage fait demi-tour), alimenté par `applyRouteEditorRepeat`/`applyRouteEditorObjectivePlan`, propagé dans tout l'historique Annuler/Rétablir et les variantes au même titre que `pois`. Comme il stocke des coordonnées absolues (pas des index), il survit sans code supplémentaire à une inversion de sens ou une rotation de boucle (cf fonctionnalité précédente) ; seul un raccourci (déplacement du départ/arrivée sur un tracé non bouclé) peut couper une zone enregistrée hors du nouveau tracé, filtrée dans ce cas (`routeEditorFilterRepeatsToPoints`, tolérance 30 m). `routeEditorExportGpx` construit aussi un waypoint par 📌 point d'intérêt existant (`ROUTE_EDITOR_POI_TYPES[].sym`, symboles Garmin standards en best-effort — un `<sym>` non reconnu par un modèle retombe sur une icône générique, le texte de l'alerte reste affiché dans tous les cas). Limite connue et acceptée : après une inversion de sens manuelle, l'ordre de déclenchement 1→N peut se retrouver inversé sur la montre (elle matche par proximité le long du parcours) — le total N reste exact dans tous les cas, non traité plus finement (complexité disproportionnée pour un cas marginal).

- **Sens du parcours + départ/arrivée déplaçables** (Itinéraires et Éditeur Parcours, 25/08) : chevrons directionnels sur la carte (plugin CDN `leaflet-polylinedecorator`, `L.polylineDecorator`/`L.Symbol.arrowHead` — aucun équivalent natif dans Leaflet core, ajouté en `<script>` juste après `leaflet.js` dans `index.html`), bouton "Inverser le sens", et déplacement du point de départ/arrivée le long du tracé **sans jamais le reroute** (aucune reformation via BRouter, contrairement au glisser-déposer d'une ancre existant côté Éditeur qui reste, lui, une reformation). Trois fonctions pures partagées, définies une seule fois dans `frontend/js/routes.js` (chargé avant `route_editor.js` dans `index.html`, même principe de partage que `haversineKm` déjà réutilisé par l'Éditeur) et réutilisées telles quelles par les deux pages : `isClosedLoopTrack` (départ≈arrivée à 50m près), `rotateLoopPoints`/`remapIndexAfterLoopRotate` (boucle fermée : le nouveau départ=arrivée choisi fait tourner le tableau de points, même forme/distance — logique reprise de `reorientLoopToClosestPoint` côté serveur, `route_generator.js`, mais appliquée en pur JS client, sans aller-retour serveur), `trimTrackPoints` (tracé non bouclé : seule option géométriquement possible sans reformer le tracé est de le raccourcir en coupant la portion avant le nouveau départ/après la nouvelle arrivée — confirmé avec l'utilisateur, `distanceM`/`ascentM`/`predictedDurationMin` recalculés dans ce cas précis via `recomputeRouteOptionMetrics`, durée mise à l'échelle proportionnellement faute de profil d'allure recalculable côté client). Aucun changement serveur necessaire dans les trois cas : `buildGpxXml`/`POST /api/routes/gpx` (route_generator.js/server.js) sérialisent déjà le tableau `points` reçu tel quel dans l'ordre — inverser/tourner/raccourcir ce tableau côté client suffit, l'export GPX suit automatiquement. Côté Éditeur Parcours, le déplacement de départ/arrivée réutilise le state-machine de modes existant (`_routeEditorMode`, valeurs `move-loop`/`move-start`/`move-finish` ajoutées aux modes déjà là) plutôt qu'un état dédié, et recalcule les stats via `routeEditorAnalyzePoints` (déjà utilisé ailleurs) après rotation/raccourci/inversion — une côte qui devient une descente (inversion) ou dont le "km 0" se déplace (rotation d'une boucle) doit être redétectée, pas juste retournée à la main.

## Conventions de travail

- **Commit après chaque correctif/fonctionnalité discrète**, message en français, format `Type: description courte` (Fix/Feat/Chore...).
- **Vérifier empiriquement dans le navigateur** après tout changement UI — les captures d'écran ne s'affichent pas dans cet environnement, utiliser `get_page_text`/`javascript_exec`/inspection DOM à la place.
- **Redémarrer le process Node** après tout changement dans `server.js`, `garmin_client.js` ou `campus_client.js` (pas de hot-reload).
- **Bump du `?v=` de cache-busting** dans `index.html` après tout changement dans un fichier JS/CSS frontend, sinon le navigateur sert l'ancienne version en cache.
- Un hook PostToolUse ouvre automatiquement un onglet `file://` parasite à chaque édition de `index.html` — le fermer et resélectionner le véritable onglet `http://localhost:3001` avant de tester.
- Pour distinguer une erreur console réelle d'un résidu périmé : comparer le `?v=` dans la stack trace de l'erreur avec le `?v=` actuel du fichier dans `index.html`.
- Compilation de l'installeur : `"/c/Users/martins/AppData/Local/Programs/Inno Setup 6/ISCC.exe" installer/allure-plus.iss` → sortie versionnée `installer/Output/AllurePlus_Setup_v{version}.exe`.
- Le dossier `plans/` (catalogue de fichiers `.aplus`) est déjà inclus automatiquement dans chaque build de l'installeur (packagé tel quel par ISCC) — s'assurer que les nouveaux plans créés entre deux versions sont bien dans ce dossier (et commités) **avant** de compiler, sinon le setup généré ne les contient pas.
